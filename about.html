02 Notes

Built over roughly three months in collaboration with Claude (Anthropic) across three surfaces: Claude Code in the terminal for code generation, edits, and deploys; Claude.ai for planning conversations and design briefs; and Claude in Chrome for live audits on the deployed site. I described what I wanted in plain language, Claude wrote and debugged the code, and the back-and-forth iterated until the page felt right. The art is the part that isn't AI — the candidate portraits, hero composition, and puppet rig were all hand-illustrated.

The product idea, the gag, the animation moments, and the taste calls are mine. The scroll wiring, the database, the deploy configuration, and most of the CSS are where Claude did the heavy lifting. The references below are what a developer would need to rebuild any individual section — each names the library, the canonical docs, the design pattern in plain words, and the file in this repo where it lives.

03 Animation references

Hero impact scroll-driven cross-fade

  • Library GSAP 3.12 + ScrollTrigger
  • Docs gsap.com/docs/v3/Plugins/ScrollTrigger/
  • Pattern Scrub timeline (timeline progress = scroll progress). Two <img> elements are stacked at the same position — normal Brady on top, shocked Brady underneath. Three tweens share one timeline: (1) the word NOT drops in via y + opacity, (2) the two Brady images cross-fade via opposing opacity tweens, (3) a CSS ::after strike-through bar on "the" scales from 0 to 1. scrub: true on the ScrollTrigger ties timeline progress to scroll progress so the user controls the pace.
  • Why this approach Stacked images cross-fade more cheaply than swapping src (no re-layout, no network round-trip). Sharing one timeline keeps the three tweens in lockstep regardless of scroll speed.
  • In repo index.html — _createHeroST() (scroll trigger), _impactTl() (timeline), .line-not CSS, the two <img> elements #hero-brady-img and #hero-brady-img-shocked

Accolades pin stamp-down on scroll

  • Library GSAP + ScrollTrigger (pin + scrub)
  • Docs ScrollTrigger — see the pin and scrub options
  • Pattern The accolades section gets pin: true, scrub: true, end: '+=Npx'. The user feels they're scrolling through the section, but actual page scroll is driving timeline progress while the pinned element holds in place. Inside that span, a chain of fromTo() tweens sequences each accolade (championships, MVPs, Super Bowl wins) onto the page with a discrete progress mark on the timeline. Each sticker uses a scale + filter-blur transform to feel like a physical stamp landing.
  • Why this approach Pinning + scrub is far more reliable than position: sticky for orchestrated multi-element sequences — it gives precise control over when within the scroll each element fires.
  • In repo index.html — .section-stage ScrollTrigger and the .word-slot / .cards-col markup it drives

Puppet dance vector character animation

  • Library Rive runtime (@rive-app/canvas) loaded via unpkg CDN
  • Docs rive.app/docs
  • Editor rive.app — the designer rigs the layered art into a state machine inside the editor; the runtime plays the resulting .riv file
  • Pattern The character is rigged from twelve named bones (head, head_hype, torso, upper_arm L/R, forearm L/R, hand_L/R open/closed, legs). On the page, scroll position drives the dance timeline's progress; a separate JS loop tracks scroll velocity and triggers a "celebration" state-machine branch above a threshold — the easter egg you see on rapid-scroll.
  • Why this approach A full Rive character is ~50 KB versus 5+ MB for a comparable GIF, stays sharp at any size because it's vector, and can respond to multiple inputs (scroll, click, hover) without re-rigging.
  • In repo index.html Rive init + scrub loop · Assets/puppet/*.riv (rigged source files)

Vote API shared real-time totals

  • Server Node + Express — expressjs.com
  • Database Postgres via pg (node-postgres) — node-postgres.com
  • Hosting Railway (Node service + managed Postgres on the same project) — docs.railway.app
  • Schema votes (player_id TEXT PRIMARY KEY, count INTEGER NOT NULL DEFAULT 0, updated_at TIMESTAMPTZ) — one row per candidate, count incremented atomically
  • Pattern Two endpoints. POST /api/vote performs an UPSERT (INSERT ... ON CONFLICT ... DO UPDATE SET count = count + 1) so concurrent voters can't lose writes. GET /api/votes returns the full tally. Express middleware sets Cache-Control: no-store on /api/* so the edge CDN can't serve stale totals (without it, desktop and mobile users saw different counts). A small in-memory rate limiter (Map keyed on X-Forwarded-For) blocks trivial spam.
  • Why this approach A relational database is overkill for five integers, but it gives correct concurrent writes for free and lets any SQL tool inspect the table.
  • In repo server.js · index.html — writeVote(), fetchServerVotes(), buildResults()

Mobile viewport URL-bar jitter fix

  • APIs window.visualViewport, dynamic viewport units (dvh / svh / lvh)
  • Docs MDN: Visual Viewport API
  • Reference web.dev: large, small, and dynamic viewport units
  • Pattern A <script> at the very top of <head> reads window.visualViewport.height (falling back to window.innerHeight) and publishes it as a CSS custom property, --vh-px. The value is grow-only: once the URL bar retracts and the viewport gets taller, that height becomes the new high-water mark and never shrinks back. CSS uses var(--vh-px, 100svh) for any pinned-section height. orientationchange resets the high-water mark.
  • Why this approach Without the shim, the URL bar's transition between expanded and collapsed states makes svh/dvh resolve to wildly different values on the same load — producing the "everything in the corner of the screen" mobile bug. visualViewport is the only API that reports the actually-visible region rather than the layout viewport.
  • In repo index.html — first <script> in <head>

05 Prompts that pushed the needle

Verbatim from the build, curated to the ones that actually moved the work forward. Five patterns kept showing up: precise bug reports with a contrast, direction-setting prompts that defined the goal, course-corrections that saved a wrong direction, meta-prompts that broke a stuck loop, and release-readiness prompts that surfaced gaps. Almost no technical jargon — Claude diagnosed the cause, I held the taste line.

Bug reports that gave Claude enough to diagnose

Symptom + where-it-works-vs-doesn't + what-not-to-break.

  1. "On mobile the first scroll has resistance. The second one feels normal. Desktop is fine. Don't change desktop."
  2. "Desktop sees 2 votes. Mobile sees 10. Same database."
  3. "I voted for Alexander on the live site and it didn't add one but it knew it was my vote."
  4. "The two are brady shocked and crown in the hero and brady shocked in the vote. Just appears as silhouettes."
  5. "The shocked Brady transition goes in and out and feels like a struggle. It used to feel good in the old file."
  6. "Now it's choppy again either I didn't notice earlier or this pin is what's doing it. The zoom in on shocked it happening slowly and the image goes in and out."

Direction-setting prompts that defined what to build

A clear goal in plain language, sized like a brief instead of a ticket.

  1. "Make the comments dev-friendly. The point of everything is that this is animation design inspo for devs and non-technical people."
  2. "We swung way too big with an about page. After you vote I want an about with a module that pops up that says Created by, Illustrations by, Rive puppet illustration drawn by..."
  3. "I'd like when someone votes for Brady same experience goes to riversgoat, doesn't ever show a vote tally for him it stays at 0 but we actually track it in the db so I can ask you how many votes does Brady have."
  4. "Module isn't formatted for mobile. Make it formatted for all devices."
  5. "Make every section every functionality clear and helpful links are good."

Course-corrections that saved a wrong direction

Direct rejection without softening, plus the redirection. Saves entire loops of polishing the wrong thing.

  1. "I hate the voice and attitude of the document."
  2. "Actually I do like the about page more than the module."
  3. "These are not two separate sections. The animation we built is replacing the existing one."
  4. "I don't like that the solution was on mobile force to the bottom poll, it also doesn't work. It should be formatted upon voting that both the poll and the sticker show on mobile screens."
  5. "This is still such the opposite of what I want."

Meta-prompts that broke a stuck loop

Pause-and-reset signals when iteration was making things worse, not better. The most valuable category.

  1. "We have about perfected the experience in desktop and mobile. There is one issue left and we should save state now because every time we attempt this we come up short. Let's think differently."
  2. "Wait is the only issue SVG is a silhouette? If that works that's a cleaner solve."
  3. "Are you using git to roll back or are you manually making changes? Isn't git the right thing to use for rollback?"
  4. "Evaluate shortcomings and do better."

Release-readiness prompts that surfaced gaps

Asked at the end of the build to find the things that weren't obviously broken but weren't actually ready.

  1. "Is this app ready for people to fill out on different devices? Me to work off another computer with git pull current version?"
  2. "What are the security concerns with putting a public email and the GitHub project link here?"
  3. "Give a prompt to share with another agent if it doesn't work and same issue of jank, transition to clean up and it will keep testing to find answer."
  4. "What about a readme in GitHub, shouldn't we have that and it be the most digestible but most comprehensive summary for a dev how to use pieces of this for their own."
